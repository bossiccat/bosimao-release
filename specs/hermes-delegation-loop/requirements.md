# Hermes 委派闭环需求

**状态：已确认（2026-08-23，用户回复“确认”）**  
**日期：2026-08-22；确认日期：2026-08-23**  
**范围：波斯猫语音前台 → backend brain → Hermes 独立后台 Agent → 状态/结果回报**

## 1. 背景与问题

当前波斯猫已经具备可工作的实时语音问答原型：Android 采集、TRTC、Windows sidecar、`rtc_bridge`、MiniCPM-o Realtime 和手机播放链路已经打通。项目也已有 `backend/app/brain/`，可以完成“意图提取 → 脱敏摘要 → 拆解 → 用户确认 → Codex GUI 注入”。

但两条管线尚未形成真正的智能体闭环：

```text
语音文本 → 直接回复（已有）
语音文本 → brain 任务草稿 → Codex GUI 注入（已有但非 Hermes）
语音文本 → Hermes 后台执行 → 持久化状态 → 结果回报（尚未实现）
```

本规格要补齐第三条路径，同时保持语音前台和后台 Agent 的职责边界清晰。目标不是把现有实时音频链路改造成 HTTP 音频转发，也不是重新实现一个通用 Agent 引擎。

## 2. 产品目标

用户可以用自然语言对波斯猫说出一个需要后台处理的请求。波斯猫应当：

1. 判断这是闲聊/即时问答，还是需要后台执行的任务。
2. 对任务做本地意图理解和脱敏，避免把原始语音或不必要的敏感信息外传。
3. 给任务分配风险等级。
4. 对低风险任务自动派发；对高风险任务在执行前进行明确的语音确认。
5. 通过 Hermes 原生 A2A 能力执行后台任务。
6. 在后台任务执行期间持久化状态，即使手机 App、sidecar、backend 或 Hermes 重启也能恢复可见状态。
7. 把“已受理、等待确认、执行中、已完成、失败或需要人工处理”等结果回报给当前语音前台，并同步给桌宠 UI。

## 3. 范围

### 3.1 本期必须包含

- 语音文本进入 backend brain 的任务路由：`direct_reply`、`delegate`、`clarify`、`deny`。
- 风险分级和确认门禁。
- `AgentBackend` 抽象，使现有 Codex GUI 通道和 Hermes A2A 通道可替换。
- Hermes 独立进程 + A2A over HTTP 的委派适配器。
- Agent Card discovery、token 鉴权、请求超时、幂等关联。
- 远程任务 ID、状态、进度摘要、错误和时间字段的持久化。
- Hermes signed webhook 的 HMAC 校验和任务状态更新。
- backend WebSocket/语音回报事件。
- backend、手机 App、sidecar、Hermes 任一方重启后的恢复和重复事件处理。
- 低风险自动派发、高风险执行前语音确认的审计记录。
- 单元、集成、协议契约和至少一轮真实本机进程联调测试。

### 3.2 本期不包含

- 不 fork Hermes，不修改 Hermes 源码，不把 Hermes 作为 Tauri `externalBin` 子进程托管。
- 不使用 ACP 作为 agent-to-agent 委派协议。ACP 的 editor-to-agent 语义不适合本闭环。
- 不自研 Hermes 已提供的通用工具调用、技能、记忆、子 Agent 和调度引擎。
- 不替换 MiniCPM-o Realtime，不改造 TRTC 媒体链，不通过 HTTP/WS 传输裸 PCM。
- 不在本期实现跨会话长期用户画像和复杂多 Agent 规划；先保证单任务闭环可靠。
- 不允许高风险任务因为“模型确信度高”而跳过用户确认。
- 不把当前 Hermes 截图监控条目误称为委派能力；监控和后台 Agent 是两个不同概念。

## 4. 用户故事

### US-1：即时问答保持自然

作为用户，我说“今天天气怎么样”或“解释一下什么是向量数据库”时，系统应继续由语音前台直接回答，不创建后台任务，不弹出无关确认卡。

### US-2：低风险任务自动交给后台

作为用户，我说“帮我查一下项目最近有哪些失败测试并总结原因”时，系统应识别为后台任务，生成脱敏任务摘要，并在风险判定为低风险且置信度足够时自动派发。系统要先口头告知“已受理/正在处理”，不要求我重复点击桌面按钮。

### US-3：高风险动作执行前确认

作为用户，我说“删除这些文件”“把报告发给某人”“修改配置并重启服务”时，系统应先说明将要执行的动作、目标和风险，等待明确的语音确认；在确认前不得调用 Hermes 执行工具。

### US-4：后台过程可见

作为用户，我可以知道任务是已受理、等待确认、排队、执行中、需要补充信息、已完成、失败还是已取消，而不是只看到一个含义不清的“连接中/已连接/监听中”。

### US-5：结果回到语音前台

作为用户，后台任务完成或失败时，即使原始语音会话已经结束，下一次语音会话也能收到简洁、准确的结果摘要；桌宠 UI 同时保留完整任务记录。

### US-6：中断和重启可恢复

作为用户，我在任务执行时杀掉并重启手机 App、重启 sidecar 或重启 backend 后，系统不能重复执行同一个任务，也不能把旧任务错误地播报成新任务；恢复连接后应显示最新已持久化状态。

### US-7：隐私可控

作为用户，原始语音、密钥、完整文件路径、凭证和不必要的个人信息不得直接发送给 Hermes。任务发送前要经过本地意图理解和脱敏摘要；审计日志也不得记录密钥或原始敏感内容。

## 5. 业务规则

### BR-1：请求路由

每个进入 brain 的自然语言请求必须归入以下一种路由：

- `direct_reply`：即时问答、闲聊、解释、澄清性对话，不需要后台工具执行。
- `delegate`：需要读取环境、调用工具、进行多步处理或延迟返回结果。
- `clarify`：目标、范围、权限、输入或验收条件不足，先向用户追问，不执行。
- `deny`：违反安全边界、超出能力范围或风险不可控，明确拒绝并说明原因。

路由置信度不足时必须进入 `clarify`，不得默认按低风险执行。

### BR-2：风险等级

本期采用三档业务风险：

| 等级 | 含义 | 默认行为 | 示例 |
|---|---|---|---|
| `low` | 只读、分析、查询或可重复的无副作用动作 | 满足置信度和参数完整性后自动派发 | 查日志、列状态、搜索代码、汇总测试结果、生成分析草稿 |
| `high` | 会写入、删除、外发、支付、改变系统状态或可能造成不可逆影响 | 执行前必须获得本次任务的明确语音确认 | 写/改文件、删除、上传/发送、支付、安装、执行系统变更、重启服务 |
| `blocked` | 法律/安全边界不允许，或无法可靠判断目标与权限 | 拒绝，不调用 Hermes | 绕过权限、索取密钥、危险破坏性操作、无法确认受影响范围 |

以下规则优先于模型判断：

- 涉及删除、覆盖、外发、支付、凭证、权限、安装、执行任意未知命令的请求，至少按 `high` 处理。
- 同一任务后续步骤只要出现高风险动作，整个任务在进入该步骤前必须再次停住确认；不能用早先对低风险任务的确认代替。
- `low` 只表示“可以自动派发”，不表示允许无边界执行。Hermes 仍必须受到目标、超时、工具和权限配置约束。
- 风险等级无法判定时按 `high` 处理，并要求澄清或确认。

### BR-3：确认语义

高风险确认必须同时绑定：`task_id`、风险摘要、目标范围、确认有效期和当前任务版本。以下回答才算明确确认：用户说“确认执行”“可以执行”“就按这个做”等与当前提示对应的肯定语句。

“嗯”“好的”“继续”在上下文不唯一时不能直接视为确认；系统应追问。确认超时、任务内容变化、目标变化或任务重试时，旧确认自动失效。

### BR-4：单任务幂等

同一 `task_id` 最多产生一个有效的远端执行关联。网络超时后重试必须携带幂等键，不得因为客户端重连而重复创建 Hermes 任务。重复 webhook 只能更新一次逻辑状态，不得重复播报或重复执行副作用。

### BR-5：状态是事实，不是 UI 文案

后台任务状态与 TRTC 连接状态、监听服务状态、语音会话状态分开建模。UI 只能根据任务状态显示任务文案，不得用“已连接”代表“任务正在执行”。

## 6. 功能需求与 EARS 验收标准

### FR-1：任务路由

**当**语音前台或文字入口向 backend 提交自然语言内容时，**系统应**返回路由类型、置信度、脱敏摘要、风险等级和缺失信息列表。

验收：

- `direct_reply` 不创建可执行后台任务。
- `delegate` 必须创建唯一 `task_id`。
- `clarify` 必须给出至少一个可回答的追问，且不得调用 Hermes。
- `deny` 必须记录拒绝原因，且不得调用 Hermes。
- 同一输入在相同策略配置下重复提交，不得产生无法关联的任务副本。

### FR-2：低风险自动派发

**当**请求被判定为 `delegate + low`、意图置信度达到配置阈值且必需参数完整时，**系统应**在一次受理流程内自动调用选定的 `AgentBackend`，并向前台发出 `accepted` 和 `running/queued` 事件。

验收：

- 用户无需再次点击桌面按钮才能开始任务。
- 自动派发前已经保存任务草稿和脱敏摘要。
- backend 重启发生在受理与派发之间时，恢复逻辑只能继续或明确标记失败，不能静默丢失。

### FR-3：高风险确认门禁

**当**请求被判定为 `high` 时，**系统必须**先创建 `awaiting_confirm` 任务并口头播报确认提示；**只有当**确认令牌与当前任务版本匹配且收到明确确认时，**系统才可**调用 Hermes。

验收：

- 未确认、拒绝、确认超时、任务内容变化时，Hermes 调用次数为零。
- 确认提示至少包含动作、目标范围和主要风险。
- 任务被修改后旧令牌不能继续使用。
- 确认、拒绝和过期均写入审计事件。

### FR-4：委派后端抽象

**当**brain 需要执行任务时，**系统应**只依赖 `AgentBackend` 抽象，不在 `BrainPipeline` 中直接依赖 Codex GUI 或 Hermes 实现。

验收：

- 现有 Codex GUI 通道可作为默认兼容后端运行。
- Hermes A2A 后端可通过配置选择，不需要修改路由规则和任务状态机。
- 后端返回至少包含 `ok`、`channel`、`remote_task_id`、错误分类和是否可重试。

### FR-5：Hermes 连接与发现

**当**Hermes A2A 后端首次启动或配置变更时，**系统应**通过 Agent Card discovery 验证 endpoint、能力、鉴权和协议版本；发现失败时不得把任务伪装成已派发。

验收：

- endpoint、token、webhook secret 从受保护配置读取，不进入源码、任务预览或普通日志。
- discovery 失败能明确区分未启动、鉴权失败、协议不兼容、超时和网络错误。
- 真实 Hermes endpoint 未通过现场协议探针前，不得声称 A2A 已联通。

### FR-6：任务消息与隐私

**当**系统向 Hermes 发送任务时，**系统应**只发送经过本地脱敏的结构化摘要、目标约束、验收条件、会话关联和必要上下文。

验收：

- 原始语音不发送给 Hermes。
- 日志和 webhook 处理记录不包含 token、secret、凭证或未脱敏敏感字段。
- `session_id`、`task_id` 和远端任务 ID 可双向关联，但不能暴露给用户作为秘密凭证。

### FR-7：任务状态持久化

**当**任务状态发生变化时，**系统应**原子持久化任务状态、版本、时间、风险、后端、远端任务 ID、进度摘要和错误信息。

最小状态集合：

```text
intent_ready
clarify
awaiting_confirm
queued
running
needs_input
completed
failed
cancelled
denied
expired
recovering
```

验收：

- 存量 `brain_tasks.json` 读取不因新增字段失败，缺省字段使用兼容默认值。
- 状态迁移非法时拒绝更新并保留原状态。
- `completed`、`failed`、`cancelled` 终态不可被重复事件回退为 `running`。
- 状态记录包含 `updated_at`，结果记录包含 `completed_at` 或失败时间。

### FR-8：Hermes 回报 webhook

**当**backend 收到 Hermes 的 signed webhook 时，**系统必须**先验证请求体原文的 HMAC、时间窗口和事件格式，验证通过后才更新任务。

验收：

- 缺失签名、签名不匹配、重放事件、未知远端任务 ID均 fail-closed。
- 合法的 `session_activity`、`tool_completion`、`turn_completion` 至少能映射到任务进度、工具结果和终态。
- 同一个事件 ID重复到达不会重复变更状态或重复语音播报。
- webhook 处理响应不会把内部 secret、堆栈或完整敏感 payload 返回给调用方。

### FR-9：状态与结果回报

**当**任务进入受理、等待确认、排队、执行中、需要补充信息、完成、失败或取消状态时，**系统应**通过统一事件模型向桌宠 WS 和语音前台发布可消费事件。

验收：

- 事件至少含 `task_id`、`session_id`、状态、发生时间、面向用户的摘要和可选进度。
- 语音播报使用短而准确的摘要，不朗读 secret、完整日志或大段工具输出。
- 原始会话已结束时，终态结果仍进入持久化的待播报队列；下一次会话可以取出且只播报一次。
- UI 可以同时显示任务状态和 TRTC/监听/语音会话状态，四者不混用。

### FR-10：失败、超时和恢复

**当**Hermes、backend、sidecar 或网络在任务执行期间不可用时，**系统应**根据错误类型进入 `recovering`、`failed` 或 `needs_input`，并给出下一步动作。

验收：

- 可重试的连接超时采用有上限的退避重试；不可重试的鉴权、协议和权限错误不盲目重试。
- backend 重启后可从持久化记录恢复未决任务；若无法确认远端事实，状态必须显示为 `recovering` 或 `needs_input`，不能伪报完成。
- Hermes 重启后，已存在的 `remote_task_id` 不被重新创建；通过 discovery/status/webhook 恢复事实。
- App 重启、TRTC 中断或 sidecar 重启只影响回报输送，不得改变已持久化的后台任务事实。

### FR-11：取消与人工接管

**当**用户要求取消一个仍可取消的任务时，**系统应**先验证任务归属和当前状态，再向 Hermes 发出取消请求或记录不可取消原因。

验收：

- 已完成或已进入不可逆执行阶段的任务不能伪装成已取消。
- 取消结果有独立审计事件。
- Hermes 不支持取消时，前台明确告知“无法撤销，只能等待结果/人工处理”。

### FR-12：观测与审计

**当**任务经历路由、风险判定、确认、派发、回报、重试、拒绝或失败时，**系统应**写入结构化审计记录。

验收：

- 可以按 `task_id` 重建完整时间线。
- 审计记录区分用户确认、系统自动决策、Hermes 回报和人工接管。
- 日志默认脱敏，保留错误分类、耗时、重试次数和关联 ID。
- 审计失败不得让高风险任务绕过确认；对低风险任务应明确记录“审计不可用”的降级状态。

## 7. 非功能需求

### NFR-1：安全

- A2A token、webhook secret、设备凭证只能来自受保护配置或凭证存储。
- webhook 使用常量时间比较；校验原文 body，不对解析后的 JSON 重新序列化后验签。
- 默认只允许 loopback 或明确配置的内网地址；不把 A2A endpoint 暴露到公网。
- 所有高风险动作 fail-closed。

### NFR-2：可靠性

- 任务状态更新和远端关联必须可幂等。
- 任务持久化采用临时文件 + 原子替换或等价机制，避免进程崩溃造成半个 JSON 文件。
- 单个 webhook handler 异常不能拖垮事件总线或 WS 广播。

### NFR-3：可测试性

必须同时具备：

- 路由与风险判定单测。
- 状态迁移与幂等单测。
- AgentBackend fake 实现集成测试。
- HMAC 正确、错误、重放和重复事件测试。
- 现有 Codex GUI 后端回归测试。
- Hermes A2A schema/Agent Card 契约探针。
- 本机独立 Hermes 进程或受控 fake server 的真实 HTTP 联调。
- backend 重启、webhook 迟到、WS 断线和手机 App 重启恢复测试。
- 任何“启动/进程/弹窗/跑通”结论必须包含真实进程、健康接口和端到端运行证据，不能只做静态检查。

### NFR-4：兼容性

- 现有 `BrainTask` 和历史任务文件向后兼容。
- `delegate_backend` 默认保持 `codex_gui`，Hermes 未启用时现有功能行为不变。
- Hermes 位于 Windows 或 WSL2 时，backend 均通过 HTTP 协议通信，不依赖共享进程内存或本地 stdio。

## 8. 初始验收场景

| 编号 | 场景 | 预期 |
|---|---|---|
| A1 | 纯闲聊/知识问答 | 直接回复，不创建后台任务 |
| A2 | 低风险查日志并总结 | 自动创建并派发，收到进度和完成回报 |
| A3 | 低风险但意图不完整 | 先追问，不调用 Hermes |
| A4 | 删除文件 | 播报风险并等待确认，未确认时零 Hermes 调用 |
| A5 | 高风险确认后执行 | 只执行当前任务版本，保存确认审计 |
| A6 | 用户拒绝或确认超时 | 任务进入 `denied`/`expired`，不执行 |
| A7 | A2A token 错误 | 进入明确失败，不无限重试，不伪报已受理 |
| A8 | webhook 签名错误 | HTTP 拒绝，任务状态不变 |
| A9 | webhook 重复到达 | 状态和语音播报只生效一次 |
| A10 | backend 重启 | 未决任务恢复；不重复创建远端任务 |
| A11 | 手机 App/WS 断线 | 后台任务继续，恢复后能取到最新状态和一次性结果 |
| A12 | Hermes 进程重启 | 已有关联任务进入恢复流程，不生成重复任务 |
| A13 | 取消可取消任务 | 取消事实可见，终态准确 |
| A14 | 凭证/密钥出现在原始输入 | 发给 Hermes 前脱敏，日志不泄露 |

## 9. 已知前提与待确认事项

以下事实来自现有代码和 ADR-023，但在进入实现前仍需现场验证：

1. Hermes 当前实际安装版本、A2A server 启动方式、Agent Card 地址和事件 payload schema。
2. Hermes 的 webhook 是否能携带稳定的事件 ID、远端任务 ID、取消结果和进度百分比。
3. MiniCPM-o `_on_text()` 到 backend brain 的正式路由入口；当前代码主要记录日志，尚未完成语音到 brain 的接线。

5. 任务结果在下一次语音会话中的播报策略：只播报最近一条，还是按优先级播报多条。
6. 真实 Hermes endpoint 联调需要的运行目录、WSL2 网络地址和 token 尚未写入本规格，也不能凭空假设。
