## 3. 根因

### 3.1 固定团队名

旧流程硬编码 `TeamCreate("mvp-dev-project")`，使不同项目和不同恢复周期争用同一命名空间，也让重启后的恢复行为不清晰。

### 3.2 通过别名绕过角色唯一性

历史团队出现 `-retry`、`-final`、`-2` 等角色名。它们不是新的专业角色，只是同一角色的重复实例，造成记录膨胀、上下文分裂和回传来源不确定。

### 3.3 调度时人为压低回合上限

架构师和设计师分别声明 40、50 回合，但历史调用曾仅提供 3 或 8 回合。需要读文件、修改、验证并回传 RoleVerdict 的任务因此在产物已部分落盘时被提前终止，随后又错误创建新别名继续。

### 3.4 失败后未优先验证落盘产物

旧流程把超时或达到回合上限等同于“没有产出”，未先检查目标文件、测试或构建证据，导致重复生成同一文档。

### 3.5 跨重启依赖后台任务句柄

后台任务句柄在 WorkBuddy 重启后可能失效。把它当成状态事实源会误判工作丢失；项目实际状态应由 Spec、计划、决策、记忆、Git 和落盘文件恢复。

### 3.6 通信范围过宽

成员曾订阅全部消息，导致成员横向通信，破坏“主理人是唯一信息中转者”的边界。

### 3.7 缺少正常收尾

部分历史团队未执行成员关闭和团队删除，留下可继续接收消息的历史上下文。

## 4. 已实施修复

已修改主理人 Agent：

`C:\Users\Administrator\.workbuddy\plugins\marketplaces\experts\plugins\mvp-dev-expert-team\agents\mvp-dev-expert-team-team-lead.md`

新增或重写的规则：

1. 启动前读取当前团队、任务、项目记忆、Spec、实施计划和落盘产物。
2. 新团队使用 `mvp-dev-{项目slug}-{会话短标识}`，不得硬编码固定名称。
3. 当前会话已有团队时禁止再次创建；跨重启最多建立一个 recovery 团队。
4. 同一 Agent ID 只允许一个成员；优先向同一成员发送恢复指令。
5. 禁止创建 `-retry`、`-final`、`-2` 等别名。
6. 默认省略调度层 `max_turns`，使用成员 frontmatter 声明；不得低于声明值。
7. 成员超时或达到上限后，先验证文件和机械证据；产物存在时只恢复 RoleVerdict。
8. 同一根因最多三轮诊断式纠错，每轮必须缩小到一个根因。
9. 成员只能向主理人回传，禁止横向通信和全量订阅。
10. 跨重启以项目文件为事实源，不依赖旧后台任务 ID。
11. 阶段结束时关闭活跃成员并清理团队上下文。

## 5. 校验器边界

内置专家管理校验器面向 `marketplaces/my-experts` 下的自建专家格式；当前对象位于 `marketplaces/experts`，属于已安装市场专家包。两者目录与注册约束不同，直接用自建专家注册器会产生“专家不在专家目录”或“缺少 settings.json”类误报。

因此本次没有强行注册、复制或迁移专家包，而是对市场包执行结构机械校验。这样可避免生成第二套同名专家或破坏市场包升级路径。

## 6. 历史记录处理决定

本次不删除 43 个 Team 配置和 393 个 Task 记录，原因如下：

- 它们是审计和问题追踪证据；
- 不直接参与项目构建、Android 运行或 RTC 链路；
- 删除历史不能修复旧启动协议；
- 新协议已阻止继续制造重复别名。

后续若用户明确要求清理，应先导出清单，区分当前活动团队与只读历史，再使用受支持的团队生命周期操作小批量处理，不直接删除底层文件。

## 7. 开工判定

专家团启动机制不再是 Phase 3 的阻断项。可以继续开工，但仍必须满足业务门禁：Phase 2 OpenAPI 必须可解析并完成架构 RoleVerdict；商业发布仍保持 FAIL，直到代码、安全、构建、RTC 实包和 Android 真机扬声器证据全部通过。
