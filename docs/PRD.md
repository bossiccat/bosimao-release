## 1. 产品定位

**一句话定位**：你的 AI 编程 agent 们的贴身监工 + 副驾——用本地多模态模型看懂屏幕，在 agent 跑偏/卡住/关键进展时主动用语音、桌宠动效和手机提醒你，并给出任务优化建议。

**产品形态**：Windows 桌面常驻的「宠物形 AI 智能助手」，本地 MiniCPM-O 4.5 多模态 9B 为大脑。

**被监控对象**：Codex（开源桌面版，重点监控，CLI 未装）/ Trae / Hermes / WorkBuddy 四目标（用户桌面实测均在跑，均为桌面端 App，有实时会话窗口）。

**安全边界（不可逾越）**：只监控 + 提醒 + 建议，**不**直接操控被监控的智能体（不注入、不发键鼠事件、不读本地日志文件内容，仅截屏 + 进程/窗口状态）。

**推送隐私边界（O-006 用户裁决）**：本地分析全程在本机完成（本地隐私承诺）；唯一离开本机的数据是"即时提醒"消息——仅发送**脱敏摘要文本**（app_id + 状态 + ≤20 字摘要 + 建议），**不附截图、不含代码片段、不含文件路径**；webhook URL 仅存于 `.env`，不入库、不随配置落盘。推送为即时通知，内容即发即弃，不做云端存储/分析。

## 2. 市场空白（4 条差异化）

1. **截屏级视觉监控**：现有监控工具全部依赖 agent 日志/telemetry/OTEL，Trae 这类 GUI 应用不暴露结构化日志——现有工具全部监控不了。本项目用本地多模态模型读屏幕，可监控任何桌面应用且无需 agent 配合改造。
2. **内容级跑偏检测**：现有工具只判断 running/idle/stuck（状态机），不能"看懂"agent 输出内容是否改错方向、陷入死循环。MiniCPM-O 可做语义级判断——现有工具全都没有的能力。
3. **主动打扰式提醒**：现有工具全是"你主动打开 dashboard 才看得到"。本项目是宠物主动说话 + 桌宠动效 + 手机推送。
4. **本地隐私**：会话日志含代码/API key，本地处理是强诉求；Agent Watch / LangSmith 均上云。

## 5. MVP 范围

### 5.1 MVP（V1 监控闭环，可验收）

1. 屏幕截屏 + 本地多模态分析（对 Codex/Trae/Hermes/WorkBuddy 四目标窗口定时截屏，MiniCPM-O 理解"当前在干什么"）
2. 跑偏/卡住/关键进展检测 + 主动提醒（桌宠动效 + 系统通知 + 语音播报）
3. 手机推送（企业微信 webhook 主选 + ntfy 备选，Provider 插件化）
4. 基础宠物形象（有机光球，监控态/提醒态双形态）

### 5.2 V1.1（全双工语音，M1 PoC 通过后开发）

5. 原生全双工语音对话（能听能说能打断，类 GPT-Live 体验）
6. 语音六态状态机前端对接 + silero-vad 门控 + 兜底降级链（sherpa-onnx + edge-tts）

### 5.3 P1 后置

7. 任务优化建议（基于检测结果 + 最近上下文的具体建议）
8. 每日会话报告

### 5.4 明确不做清单

1. 不操控被监控 agent（安全边界）
2. 不做 agent 日志解析/框架 SDK 接入（依赖日志的路线覆盖不了 Trae）
3. 不做云端 SaaS/账号体系（本地优先隐私）
4. 不做宠物养成玩法（喂食/升级/商店）
5. 不做 token 成本监控（非差异化）
6. 不做多语言/国际化
7. 不做推送内容的云端存储/分析——推送仅为即时通知，脱敏摘要即发即弃，不留存、不聚合、不用于训练

## 6. 功能需求（EARS 句式）

### 6.1 监控（M-*）

- **M-1**：WHEN 应用启动，THEN 自动加载 config/monitors.yaml 中的监控目标并按轮询间隔开始截屏分析。
- **M-2**：WHEN 被监控窗口可见，THEN 每 5-8s 捕获一帧并交给本地多模态模型分析，单帧端到端判定 ≤ 4s。
- **M-3**：WHEN 用户进入语音对话，THEN 监控轮询降频至 10-15s/帧。
- **M-4**：WHEN 被监控窗口最小化或捕获失败，THEN 降级为 DXGI 兜底或仅窗口状态监控，并记录降级原因。

### 6.2 检测与提醒（D-*）

- **D-1**：IF 某 agent 连续 3 帧判定状态不变 AND 持续超时 120s，THEN 判定为"卡住"并触发提醒（P50 响应 ≤ 2s）。
- **D-2**：IF 某 agent 判定为"跑偏"（内容级偏离目标），THEN 触发提醒并附建议。判定准确率以 PoC B1 固化的样例集（≥10 张真实截图人工标注）为验收基线。
- **D-3**：WHEN 提醒触发，THEN 按四级渐进打扰递进（**递进=按严重度定级，非时间累进**）：①状态点变色 → ②桌宠微动 → ③桌宠浮起放大脉冲 → ④语音播报 + 手机推送（仅 4 级）。分级规则：stuck 超时=4 级、off_track=3 级、恢复=1 级。
- **D-4**：WHEN 检测到恢复（状态变为有进展），THEN 自动清除卡住/跑偏状态并通知。

### 6.3 语音（V-*，V1.1）

- **V-1**：WHEN 用户点击宠物或按下唤醒键，THEN 进入 Listening 状态。
- **V-2**：WHEN 用户说话结束，THEN 端到端响应首字 ≤ 1.5s（原生全双工）。
- **V-3**：WHEN 宠物正在说话 AND 用户开口，THEN 500ms 内打断并进入 Listening（barge-in，变形不重置；"变形不重置"依赖 PoC B3 实测验证）。
- **V-4**：WHEN 原生全双工不可用，THEN 自动降级半双工（sherpa-onnx STT + edge-tts TTS），分轮回话 ≤ 2.5s。
- **V-5**：WHEN 静默超时（15s 无对话），THEN 自动回落 Monitoring 状态。

### 6.4 推送（P-*）

- **P-1**：WHILE 推送提醒时，系统必须仅发送脱敏摘要文本（app_id + 状态 + ≤20 字摘要 + 建议），不得附截图、不得包含代码片段或文件路径；WHEN 触发 4 级提醒，THEN 通过当前启用的 Provider 推送手机。
- **P-2**：WHEN 主 Provider（企业微信）失败，THEN 自动熔断切换备选（ntfy）。
- **P-3**：WHEN 推送成功/失败，THEN 记录到 metrics 日志供审计。

### 6.5 宠物 UI（U-*）

- **U-1**：WHEN 应用运行，THEN 宠物以透明窗口常驻桌面（监控态 64-96px / 透明度 20-40%）。
- **U-2**：WHEN 触发 3 级及以上提醒，THEN 宠物浮起放大至 120-160px 并以语义色 2Hz 脉冲。
- **U-3**：WHEN 系统开启 reduced-motion，THEN 全部动效降级为静态颜色 + 透明度变化。

## 7. 验收标准

### 7.1 V1（监控闭环）

- [ ] 四窗口（Codex/Trae/Hermes/WorkBuddy）正常出帧，60 帧有效帧率 ≥ 95%
- [ ] 手动构造卡住场景 → 桌宠提醒态正确 + 系统通知 + 手机推送收到
- [ ] 手机推送可达性（e2e 手动步骤）：用户提供 webhook → 触发 test-push → 手机收到 → 记录推送时间与摘要内容
- [ ] config 改值生效：修改 detection.yaml 阈值（如 5/180/3）→ 状态接口返回新值（回归防 P0-2 复发）
- [ ] 恢复后状态自动复位
- [ ] e2e_verify.py 全流程通过 + 单测/集成测试全绿 + 回归率 0

### 7.2 V1.1（全双工语音）

- [ ] 六态状态机（Idle/Monitoring/Listening/Thinking/Speaking/Alerting）事件驱动正确
- [ ] 全双工端到端 ≤ 1.5s（P50）；打断响应 < 500ms，可连续打断 3 次
- [ ] 兜底降级链可用（原生失败自动切半双工）
- [ ] 监控与语音并发不崩（对话期降频生效）
