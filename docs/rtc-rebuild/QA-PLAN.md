## 1. 核心指标（验收锚点）

### 1.1 端到端延迟（说话结束 → 回复首音）

> 参考基线：现 mock 手机直连网关实测首音 **~1s**（`tmp/e2e_apm_gateway.py`）；MiniCPM-o API TTFT 实测 875–1034ms（docs/specs/mobile-voice-spec.md §8.2 回填）。跨网加 RTC 链路，预算拆解：手机采集+上行 ~50-150ms + RTC 云转发 ~50-200ms + PC 端 RTC→apm_bridge ~10-50ms + API TTFT ~900-1050ms + 下行 ~50-200ms ≈ 1.1-1.7s。

**验收指标：**

| 指标 | 目标值 | 测量方法 | 采样 |
|------|--------|----------|------|
| 端到端首音延迟 P50 | **≤ 2.0s** | 手机端打点：`speech_end`（VAD 说完）→ 收到第一块可播放下行音频 | ≥ 20 轮对话 |
| 端到端首音延迟 P95 | **≤ 3.0s** | 同上 | ≥ 20 轮 |
| 打断响应（barge-in） | **< 500ms（P50）**（PRD V-3） | 开口参考点（本地采集回调能量阈值打点，测试辅助，不参与控制）→ 下行停止（播放停止打点） | ≥ 10 次 |
| 静默回落 | 15s 无对话 → Monitoring（PRD V-5） | 手机六态状态机打点 | 每场景 1 次 |

**测量方式约束（防作弊）：**
- 端到端延迟**必须在手机端打点**（speech_end 到播放首音），不允许用 PC 侧日志自证。
- 计时起点=用户说完（VAD 判定 speech_end），终点=手机扬声器输出首音，**不是**收到首包（播放缓冲会虚增/虚减）。
- 首音判定：可播放的语音帧（非纯静音帧），由手机端播放线程标记。

> **mic handoff 对打断测量口径的影响（ARCHITECTURE.md §5.1，v1.1 对齐）**：
> 会话期间 mic 由 TRTC SDK 独占（本地 MicRecorder 已停），**打断控制不再依赖本地 VAD**，而是：
> - 打断触发：TRTC 播放状态（`onRemoteUserAudioStatus` / 远端音频状态）+ 六态状态机驱动 → 停播下行 + 切 Listening；
> - 语义层打断：MiniCPM-o 原生 barge-in（手机持续上行推音频，模型随时压扁回复），手机侧不做轮次门控。
> 因此「打断 <500ms」的**证据是 SDK 播放状态变化 + 状态机切态打点**，不是本地 VAD 事件。测量时「开口时刻」参考点用本地采集回调（`onLocalAudioFrame`）能量阈值打点——该打点**只做测试度量，不参与打断控制**，避免自证偏差。

### 1.2 长时间通话稳定性

| 指标 | 目标值 | 测量方法 |
|------|--------|----------|
| 30 分钟连续通话不掉线 | **30min 内 0 次断开**（SDK 层面 join 状态不丢） | 真机通话 30min，记录 join 状态、断线次数、重连次数 |
| 通话中音频质量 | 无持续爆音/卡顿/断续；主观 MOS ≥ 3.5 | 30min 录音回放人工听测 + 卡顿事件计数（播放 buffer underrun 次数 ≤ 10 次/30min） |
| 电脑端内存稳定 | 30min 内存增长 ≤ 100MB（无泄漏） | PC 端进程 RSS 采样，起止对比 |
| 手机端功耗 | 通话期额外功耗 ≤ 5%/30min（参考 M1 基线） | 真机电量打点（可选，记录机型） |

**通过标准：** 30min 内 0 次非预期断开；若发生断开必须满足 §1.3 自动恢复，且**恢复后会话不丢**（上下文延续，用户无需重新唤醒/重新提问）。

### 1.3 断网自动恢复

| 场景 | 恢复目标 | 通过标准 |
|------|----------|----------|
| 手机 WiFi↔4G 切换（断网 <10s） | **恢复 ≤ 5s（P50）/ ≤ 10s（P95）** | RTC SDK 自动重连（不依赖应用手动重连）；恢复后直接继续对话 |
| 电脑断网重连（断网 10-60s） | **恢复 ≤ 10s**（网络恢复后起算） | PC 端 RTC 对端自动重新进房；手机端无感或短暂中断提示 |
| 手机飞行模式 60s 后恢复 | **恢复 ≤ 15s**（网络恢复后起算） | 同上 |

> 参考：旧 WS 中继 M2 目标为「断线重连 ≤30s」（mobile-voice-spec §12）。**RTC 成熟方案必须显著优于该值**——SDK 内置重连，目标收紧为 ≤5s P50。这是「推倒重做为 RTC」的验收红利，若达不到需说明原因并回退评审。

## 2. 连接稳定性场景（每场景给通过标准）

### 场景 A：手机 WiFi ↔ 4G 切换

**步骤：**
1. 手机连 WiFi 进房，正常对话一轮。
2. 通话中（或静默）关闭 WiFi 切 4G（或飞行模式 5s 再开）。
3. 观察状态：手机端 RTC 状态回调（disconnected → reconnecting → connected）。
4. 网络恢复后说第二句话，验证可继续对话。

**通过标准：**
- [ ] 切换后自动重连，**无需用户操作**；P50 ≤ 5s、P95 ≤ 10s。
- [ ] 恢复后新一轮对话端到端首音仍 ≤ 2s（不因重连降级）。
- [ ] 切换期间音频无脏数据（无爆音/杂音帧播放）。
- [ ] 手机端状态机不卡死在 listening/thinking（重连期间 UI 有明确「重连中」或短暂静默，恢复后回 monitoring）。

### 场景 B：电脑断网重连

**步骤：**
1. 正常通话中，拔掉电脑网线 / 断 WiFi（10s 后恢复）。
2. 观察 PC 端 RTC 对端状态与日志。
3. 网络恢复后，手机端再说一句话。

**通过标准：**
- [ ] PC 端 RTC 对端在网络恢复后 **≤ 10s** 自动重新进房（进房回调 connected）。
- [ ] 手机端不主动退房（SDK 保持房间），远端流恢复后音频继续。
- [ ] 恢复后对话正常，**无需手机重新进房/重新配对**。
- [ ] PC 端 apm_bridge 会话未因断网被误杀（超时机制需区分「网络断」与「用户停」）。

### 场景 C：RTC 房间异常退出清理

**步骤：**
1. 手机 App 强杀（kill process）→ 房间异常退出。
2. 电脑端观察：远端用户离开事件、房间状态、会话资源。
3. 手机重新进房（新 session），再正常对话。
4. 异常退出后，PC 端 apm_bridge / voice session 无残留占用（显存、进程、内存）。

**通过标准：**
- [ ] 手机强杀后 PC 端在 **≤ 60s** 内收到远端离开回调并清理会话资源（`onRemoteUserOffline` / `onUserLeft`）。
- [ ] 清理后 apm_bridge 的 MiniCPM-o 连接正确关闭（无连接泄漏；重连额度不被耗尽）。
- [ ] 手机重新进房可立即对话，**不残留旧会话状态**（不会出现「上一轮回答还在播」）。
- [ ] 房间号复用不冲突：同一用户重新进同一房间成功（SDK 进房幂等）。
- [ ] 异常退出不留脏数据：PC 端 session 计数、状态快照、埋点数据一致。

### 场景 D：并发/多端边界（记录性，不做硬门）

- 同一房间是否允许手机+PC 各一端的约束（RTC 房间通常允许多人，需确认方案约束为 2 人）；若房间被第三方误入，音频不串流（鉴权/房号随机化）。
- 通过标准：房间有 token/签名鉴权，非授权端无法进房收流。

## 4. 新测试设计（RTC 层怎么测）

> 设计原则：**三层金字塔**——单测（mock RTC 引擎，快）→ 集成（本地回环/双端 mock，中）→ E2E（真机跨网，慢但权威）。RTC SDK 依赖网络，不能全压在真机上，也不能全用 mock 自证。

### 4.1 L0 单测：RTC 对端包装类（Python 侧，mock RTC 引擎）

**被测对象：** PC 端新增的 RtcPeer 包装类（对齐 ARCHITECTURE.md §5.2 接口抽象：`enter_room() / exit_room() / on_remote_audio(frame) / on_remote_user_enter/leave / on_connection_lost/recovery`）。

**方法：** 依赖注入 FakeRtcEngine（实现 RTC SDK 同签名接口），不连真实 RTC 云。

**用例清单（先写，重构后对照）：**
1. 进房成功 → 状态 connected，回调顺序正确（enterRoom success → onEnterRoom）。
2. 进房失败（房间不存在/网络错误/token 失效）→ 错误回调 + 按退避重试（验证重试次数/间隔配置）。
3. 远端用户进房（手机）→ `onRemoteUserEnter` 回调 → 启动接收远端音频。
4. 远端音频数据回调 → 正确转发到 apm_bridge（16k s16 PCM 帧格式正确，无乱序/丢帧静默）。
5. **（v1.1 新增）上行持续转发无轮次门控**：RtcPeer 对上行音频**不做 VAD/轮次判定**，持续转发到 apm_bridge——这是 MiniCPM-o 原生 barge-in 的前提（模型靠持续上行随时压扁回复）。注入「上行在静音后停止转发」时必须有测试变红。
6. 远端用户离开（手机强杀）→ `onRemoteUserOffline` → 清理会话（§2 场景 C 单测层验证）。
7. 本地断网 → `onConnectionLost` → 重连流程触发（次数/退避）→ 重连成功恢复。
8. 退房（正常）→ 资源释放（连接关闭、无泄漏）。
9. 边界：进房后立即退房、重复进房、进房超时（配置超时时间内无回调）。
10. 音频格式转换：RTC 回调 PCM（f32/s16，采样率 48k/16k）→ apm_bridge 所需 16k s16，纯函数单测 + 变异加固（采样率换算、字节序）。

**手机端 RtcClient.kt 的 L0 单测（Android JVM，mock TRTC SDK）：**
- 进房/退房状态机（enterRoom 成功/失败/重复调用幂等）。
- **打断状态机（v1.1 对齐 mic handoff）**：mock TRTC 回调 `onRemoteUserAudioStatus`（speaking→silent/打断）→ 断言六态 Speaking→Listening 切态 + 下行停播动作被触发；**不依赖本地 VAD**。
- 重连回调（onConnectionLost/onTryReconnect/onConnectionRecovery）→ UI 状态驱动正确。
- **回调名/签名待核验（对齐 §6.4 幻觉依赖防线）**：TRTC Android SDK 实际回调名以锁定的 SDK jar 为准（fe-mobile Phase A 核对 `onRemoteUserAudioStatus` / `onTryToReconnect` / `onUserVoiceVolume` 等，差异回写 ADR）。**mock 的触发点必须参数化（按回调名注入）**，fe-mobile 确认真实签名后只改 mock 接线、不改用例断言——防止「凭印象写回调名」的幻觉接口失效。

**变异定向加固点（§5 纪律）：** 重连退避计算（指数退避 1→2→4→8→上限）、远端离线清理分支、音频格式转换采样率、上行持续转发门控。注入「退避写成线性」「离线不清会话」「采样率换算错」「上行静音后停发」时，必须有测试变红。

### 4.2 L1 集成：本地回环 + 双端 mock（连真实 RTC 云但本地双端）

**方法 A —— 本地双端回环（首选，验证 RTC 链路真实可用）：**
- 同一台电脑跑两个 RTC 客户端：`RtcPeerA`（模拟手机，发 WAV 音频）+ `RtcPeerB`（模拟 PC 对端，接音频）。
- 进同一房间 → A 发 `tmp/poc_b3_ask_16k.wav` → B 收到完整音频 → 断言字节完整性（静音帧/时长/能量）。
- 这验证：进房、房间内音频流转发、远端音频回调、退房——**不依赖真机**，可在 CI/本地反复跑。

**方法 B —— PC 网关 + 真 MiniCPM-o 集成（复用现有 e2e）：**
- mock RTC 对端（替代 mock 手机）进房 → 音频经 RTC → PC RtcPeer → apm_bridge → MiniCPM-o → 回复音频经 RTC 下行 → mock 对端收。
- 断言：首音延迟、双轮对话、打断（§3.2 三项全过）。
- 这是**跨网前的最重要集成门**：能过说明「RTC 传输 + apm_bridge」整条 PC 侧链路正确，真机问题只剩手机端 SDK 集成。

**方法 C —— 手机端 SDK 无头模式（Android JVM/仪器测试）：**
- RTC SDK 支持本地预览/回环（TRTC `startLocalAudio` + 本地回环 / 声网 loopback），在无头测试环境验证 SDK 采集/播放接管不崩。
- 若 SDK 无纯无头回环，用 Espresso/仪器测试连测试房间，断言进房回调 + 远端流事件。

### 4.3 关键：RTC 层测试的「传输真实性」验证

- RTC 层测试必须**至少包含一条连真实 RTC 云的路径**（§4.2 方法 A/B），否则「mock 引擎全绿 + 真云不通」无法发现（幻觉依赖/接口失效模式，见 §6.5）。
- 真云路径用例数可以少（1-2 个），但必须是 CI 的必跑项或验收门禁项。

## 6. 测试完整性反作弊门（P0 级门禁，验收时逐项执行）

> 重构 = 大改，AI 生成代码会作弊（删测试换绿、弱化断言、加 skip、硬编码）。验收第一步先过此门，发现任一即 P0 阻断。

| # | 检测项 | 方法 | 阻断条件 |
|---|--------|------|----------|
| 1 | 测试文件/用例被删 | `git diff --name-status HEAD~1 -- '*test*'` | 出现 `D`（删除）且无迁移记录 |
| 2 | 断言数下降 | 对比开发前后 `expect(/assert ` 数量 | 总断言数下降（排除已迁移等价替换） |
| 3 | 新增 skip/xfail/.only/focus | `git diff HEAD~1 -- '*test*' | grep '^+' | grep -i 'skip\|xfail\|\.only\|focus'` | 任何新增 |
| 4 | 硬编码断言 | 人工审查：断言值是否来自实现返回值而非 Spec 定义 | 断言绑实现输出 |
| 5 | 测试框架配置篡改 | `git diff HEAD~1 -- pytest.ini pyproject.toml build.gradle.kts` | scripts.test/coverage 阈值被调低 |
| 6 | 实现 diff 与测试 diff 未分离评审 | 提交记录检查 | 同一 commit 混入测试改动且无说明 |

### 6.1 回归率（一等指标）

- **定义：** 重构后由绿转红的旧行为/用例数。
- **判定：** 回归率 ≠ 0 即**不算完成**，必须先消回归再谈上线。解决率（新 RTC 功能达标）与回归率并列上报。
- **基线：** 重构前对 `tests/unit` 全量跑一遍存基线（绿），重构后重跑，任何由绿转红即计入。

### 6.3 安全测试（RTC 场景必查项）

| 风险 | 测试方法 | 预期 |
|------|----------|------|

### 6.4 失效模式核对（6 类，验收时逐项）

| 失效模式 | 检查项 |
|----------|--------|
| Happy-path 偏差 | 错误/超时/重连分支有测试；不只测成功进房 |
| 沉默逻辑错误 | 核心逻辑（重连退避/离线清理/格式转换）做了变异加固，有杀手测试 |
| 幻觉依赖接口 | RTC SDK 方法/回调名对照官方文档核验；依赖版本已锁定且存在 |
| 缺失系统上下文 | 房间鉴权、免费额度限制、SDK 自动重连开关、回声消除开关被显式配置并验证 |
| 性能盲区 | 音频转发无逐帧阻塞 IO；30min 内存无泄漏 |
| 静默缺失 | 构建/lint 必过；RTC SDK 初始化失败分支有错误上报 |
